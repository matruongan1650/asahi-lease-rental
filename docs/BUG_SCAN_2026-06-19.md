## 🔴 HIGH

### 1. [logic] Editing a company name jumps the open detail view to a different (or no) customer because the selection key is a sort-position-derived code
**`src/components/AdminCustomerManagement.tsx:255-261`** (admin-customer-mgmt)

- **問題:** Customer identity/selection key is `code = `C-100${idx+1}`` where idx is the index into `uniqueCompanies`, which is sorted by company name (line 248-250). `selectedCustomerId` stores this position-derived code. When `handleUpdateCustomer` renames a company (updateUser with new companyName, lines 461-493), the next render re-sorts `uniqueCompanies`, so every company at or after the rename's new alphabetical position shifts index, and the `C-100x` codes are reassigned to different companies. `selectedCustomerId` is not updated, so `customer = customersData.find(c => c.code === selectedCustomerId)` (line 650) now resolves to a DIFFERENT company, or to undefined (renders null, line 651).
- **影響:** After an admin edits a customer's company name (a normal action), the detail screen silently switches to another company's data or blanks out. Worse, the Edit modal footer/onSubmit re-resolve `customersData.find(c => c.code === selectedCustomerId)` (lines 1718, 1722), so a subsequent save could write fields onto the wrong company. The contract-file panel (filtered by selectedCompanyName, line 320-321) and 代理ログイン target (handleLoginAsCustomer, line 693) also bind to the now-mismatched record — risk of editing/login-as the wrong customer.
- **修正案:** Derive the customer key from stable data (e.g. mainUser.id or a slug of the trimmed companyName) instead of the sorted array index, and/or after rename update selectedCustomerId to the new code (or clear it). Keying by mainUser.id avoids reshuffling entirely.

### 2. [data-integrity] Purchase-order ID generated from Math.random with no uniqueness check (collision → overwrite/duplicate)
**`src/pages/Admin/AdminSuppliers.tsx:121`** (admin-suppliers)

- **問題:** New 発注 (purchase order) IDs are generated as `"PO-" + Math.floor(2200 + Math.random() * 800)`, giving only 800 possible IDs (PO-2200..PO-2999) with no check against existing IDs. OrderBus.push uses this id as the record key. Once a few hundred POs exist, collisions become likely; a collision either overwrites an existing PO or creates a duplicate key.
- **影響:** A colliding ID silently overwrites or duplicates a purchase order. Because 買掛金 (payables) is aggregated from purchaseOrders (payableBySupplier, lines 73-79), losing or duplicating a PO corrupts the accounts-payable KPI for that supplier — a money/data-integrity error.
- **修正案:** Use a collision-resistant ID, e.g. `"PO-" + Date.now().toString().slice(-6)` plus a short random suffix, or derive from a server-side counter, and verify the ID is not already present in purchaseOrders before pushing.

### 3. [security] Plaintext password comparison in admin login handler
**`src/components/AdminAuthGate.tsx:231`** (admin-ui-auth)

- **問題:** handleLogin compares the stored user password directly to the entered password in plaintext on the client: (target.password || "") !== password. This confirms the known infra TODO (plaintext stored passwords) is still present and is being read/compared on the client. The full user list (with passwords) is loaded into the browser (users from useUser) for this comparison to even work, meaning every admin client holds all users' plaintext passwords in memory.
- **影響:** All user passwords are shipped to and compared in the browser in plaintext, exposing credentials to anyone with client access / a memory dump / the network payload, and enabling offline credential theft. Authentication should never be performed by client-side plaintext comparison.
- **修正案:** Move credential verification to the server (hash+salt, e.g. bcrypt/argon2) and never send other users' password fields to the client; the client should POST credentials and receive a session/token.

### 4. [data-integrity] 伝票番号 (docNo) regenerates on every render via Math.random()
**`src/components/AdminDocDrawer.tsx:212`** (admin-ui-auth)

- **問題:** docNo is computed as a plain const in the component body using Math.random() on EVERY render. React re-renders this drawer on every keystroke (customer/site/date/note/items state changes), so the displayed 伝票番号 changes continuously while the user fills the form. The value finally submitted in submit() (lines 220, 222, 262) is whatever the last render produced, not the number the user saw earlier. Worse, the ID space is tiny — Math.floor(4400 + Math.random()*900) yields only 900 possible values (4400–5299) with no uniqueness check — so collisions across documents are likely. onCreate() uses this docNo as the record `id`, meaning two created documents can silently share the same id, causing key collisions / overwrites downstream.
- **影響:** The document number shown to the admin is unstable (flickers as they type) and the persisted invoice/contract id is non-unique and collision-prone. Two 契約/請求 records can collide on the same id (e.g. INV-R-4502), risking overwrite or mismatched references in order/invoice generation.
- **修正案:** Generate docNo once per open in a useEffect/useState (or useMemo keyed on [open, kind]) and derive uniqueness from a counter or timestamp instead of a 3-digit random number, e.g. setDocNo(`${m.code}-${Date.now().toString(36)}`) when the drawer opens.

### 5. [data-integrity] Non-atomic read-modify-write on product stock during 入庫 (lost update / stock drift)
**`src/pages/Admin/AdminStockIn.tsx:97-99`** (admin-vehicles)

- **問題:** handleSaveStockIn reads the product's current stock from the `match` object captured from the rendered `supplyProducts` array (a snapshot of context state), then writes back `Number(match.stock || 0) + Number(qty)` as an absolute value via OrderBus.patch. patch (orderBus.ts:570-582) does a full-record merge with this absolute value — it is not a server-side increment. If the local `match.stock` snapshot is stale (concurrent stock-out/in from another tab/device/the cloud-sync layer, or a re-render lag), the addition is computed against the wrong base and the other party's update is silently overwritten. The KNOWN infra TODO explicitly lists 'non-atomic stock updates (race window)' — this screen is one of the offenders.
- **影響:** Concurrent 入庫/出庫 operations (multiple admins, or admin + automatic order-confirmation deduction) can lose updates, causing physical stock to drift from recorded stock. Inventory becomes unreliable.
- **修正案:** Compute the new stock from a fresh read at write time (e.g. OrderBus.getAll('products').find(...).stock) inside patch, or add a server-side atomic increment (stockDelta) to the API/patch layer rather than writing an absolute value derived from a UI snapshot.

### 6. [data-integrity] Stocktake of one vehicle overwrites the shared product's entire stock
**`src/pages/Admin/AdminStocktake.tsx:176-200, 309-312`** (admin-warehouse)

- **問題:** For each vehicle row, system is computed as Number(v.stock ?? linkedProduct?.stock ?? 1) and productId = v.productId || v.id. When a vehicle has no own stock field, its 'system' (book quantity) is taken from the LINKED product's stock, and on finalize the loop writes that vehicle's counted value back to BOTH the vehicle AND the shared product: OrderBus.patch("products", row.productId, { stock: row.counted }). If several vehicles reference the same product, or the linked product also represents a pooled supply quantity, counting a single physical vehicle (counted=1) overwrites the whole product's stock to 1. Multiple vehicle rows pointing at the same productId also race: the last diff row processed wins (lost update).
- **影響:** Finalizing a stocktake can silently clobber a product's true stock with a single vehicle's count (e.g. set to 1), or have two same-product vehicle rows overwrite each other. Causes stock drift / data corruption in products.stock, breaking the 在庫 ledger invariant.
- **修正案:** Do not write a vehicle's counted value into products.stock. Reconcile vehicle counts only against vehicles.stock (row.vehicleId), and reconcile products.stock only from genuine supply rows. If a vehicle truly owns a product quantity, ensure productId is unique per row and aggregate counts per productId before patching.

### 7. [race-condition] Non-atomic read-modify-write of products.stock on 入庫/出庫 loses concurrent updates
**`src/pages/Admin/AdminWarehouse.tsx:349, 358-360, 380-381`** (admin-warehouse)

- **問題:** handleSaveSupplyAction reads currentStock from the products render snapshot (productForSupply -> product.stock) and then writes an absolute new value via OrderBus.patch("products", id, { stock: currentStock + qty }) / { stock: Math.max(0, currentStock - qty) }. Between the snapshot read and the patch, the stock can change from another tab/device (cross-tab sync via OrderBus) or from an order confirmation that deducts stock (deductOrderStock). Because patch overwrites stock with a value computed from the stale snapshot, the concurrent change is lost.
- **影響:** If an order confirmation (受注確定) deducts stock or another admin adjusts stock between opening the warehouse view and saving an 入庫/出庫, that change is overwritten — stock drift and lost deductions, violating the deduct-at-confirm invariant.
- **修正案:** Make stock updates a relative delta (patch should accept an increment) or re-read the latest stock from OrderBus.getAll("products") immediately before computing nextStock, ideally under an atomic compare-and-set or server-side increment.

### 8. [data-integrity] Predictable 4-digit random order numbers collide, producing duplicate order/invoice numbers
**`src/context/OrderContext.tsx:111`** (contexts-data)

- **問題:** addOrder generates the human-facing orderNumber as `#ORD-<year>-<Math.floor(Math.random()*10000)>` with no uniqueness check. Within one calendar year there are only 10,000 possible values and no guard against reuse, so two distinct orders can share the same orderNumber. This number is not just cosmetic: AdminDataContext derives invoice numbers from it by slicing the last 4 digits (`"INV-R-" + orderNumber.replace(/\D/g,"").slice(-4)` and the INV-S- variant in useAdminOrders, lines 191/202), and deriveAdminData uses orderNumber as the React/list key (recentTx id). The unique DB id (line 110) is separate and unaffected, but the orderNumber a customer and admin actually see/print can duplicate.
- **影響:** Two different rentals can be issued the same order number and therefore the same derived 請求書/invoice number (INV-R-xxxx / INV-S-xxxx). Customers and admins cannot distinguish the orders; invoice/billing reconciliation and any UI keyed on orderNumber (recentTx list keys) collide. Probability of at least one collision becomes significant after only a few hundred orders/year (birthday-paradox: ~50% by ~118 orders).
- **修正案:** Derive the order number from a monotonic server sequence or from the already-unique id, e.g. include a timestamp/counter component (`#ORD-${year}-${Date.now().toString(36)}`) or query the backend for the next sequence, instead of a 4-digit Math.random().

### 9. [security] Auth bypass: orders with no userId are viewable by unauthenticated users (IDOR) — desktop

### 10. [data-integrity] Zero/undefined rentPrice item silently dropped from remaining list, misclassifying partial return as full (desktop)

### 11. [security] mail.php is an unauthenticated open mail relay when mail_api_enabled is on
**`public/api/mail.php:11-28`** (php-aux)

- **問題:** Every other data/aux PHP endpoint (store.php, sync.php, query.php, upload.php, auth.php) calls require_api_token(), but mail.php does NOT. Its only gate is the boolean config flag mail_api_enabled. When that flag is enabled, ANY anonymous request can POST {to, subject, message} and the server sends arbitrary email through the company's authenticated SMTP account (smtp.gmail.com with the stored app password). There is no token check, no current_user() check, and no rate limiting.
- **影響:** If the operator ever flips mail_api_enabled to true, the endpoint becomes an open relay: attackers can send unlimited spam/phishing as アサヒリース株式会社 from the real corporate Gmail/Workspace account, getting the domain blacklisted and impersonating the company to its customers. The flag is the only thing standing between safe and fully-exposed.
- **修正案:** Add require_api_token(); (and/or a current_user() privileged-role check) at the top of the try block, exactly as store.php/sync.php/query.php/upload.php do, in addition to the mail_api_enabled flag.

### 12. [security] Node/Vercel sync API (server/app.ts) has NO authentication on any endpoint
**`server/app.ts:55-163`** (php-aux)

- **問題:** The PHP backend protects /store, /sync, /query, /upload with require_api_token(). The shared Express app used by both server/dev.ts and the Vercel serverless function api/[...path].ts has no equivalent. ### 13. [security] Node /api/upload allows SVG, reintroducing stored XSS that the PHP version deliberately blocks
**`server/app.ts:26-28`** (php-aux)

- **問題:** upload.php intentionally omits svg+xml from its extension map with an explicit comment that same-origin SVGs can execute JavaScript (stored XSS). The Node EXT_MAP includes 'svg+xml': 'svg', so /api/upload accepts a data:image/svg+xml;base64 payload, writes it as a .svg file, and serves it from the same origin via express.static at /api/uploads (line 60). The returned URL points to that same-origin SVG.
- **影響:** An attacker can upload an SVG containing <script> as a 'photo'/'signature', then any user (admin/staff/customer) who opens that same-origin /api/uploads/<sha1>.svg URL executes attacker JS in the app origin — stealing tokens/session, performing actions as that user. The PHP side blocks exactly this; the Node/Vercel path silently allows it.
- **修正案:** Remove the 'svg+xml': 'svg' entry from EXT_MAP so the Node uploader matches upload.php and rejects SVG uploads (or serve uploads with Content-Disposition: attachment and a restrictive Content-Security-Policy).

### 14. [security] User passwords compared in plaintext (stored unhashed)
**`public/api/auth.php:52-56`** (php-core)

- **問題:** Authentication reads $user['password'] straight from the stored user record and compares it to the submitted password with hash_equals on the raw values. ### 15. [data-integrity] DELETE path bumps rev outside a transaction, can drop deletions from sync cursor
**`public/api/store.php:106-114`** (php-core)

- **問題:** The POST path was deliberately wrapped in a transaction (see the comment at lines 66-69) so that rev allocation via next_rev() and the row write commit together and stay in rev order; otherwise the rev_counter row lock is released before the record write commits and the sync increment cursor can permanently skip records. The DELETE path repeats exactly the bug the POST comment warns about: next_rev() is called (line 111) and the soft-delete UPDATE runs (lines 112-113) in autocommit with NO beginTransaction/commit. next_rev() commits the rev_counter increment immediately and releases its lock, then the records UPDATE commits separately. Under concurrency the deletion's rev can become visible/committed out of order relative to its rev number.
- **影響:** A delete can be skipped by sync.php's incremental cursor (since=maxReturnedRev), so a record deleted on the server stays visible forever on other clients (e.g. a cancelled/removed order, deleted user, or stock record never disappears). This is the same permanent-data-loss/divergence class the POST transaction was added to prevent.
- **修正案:** Wrap the DELETE in the same transaction as POST: $pdo->beginTransaction(); $rev = next_rev($pdo); /* UPDATE */; $pdo->commit(); (the existing catch block already rolls back on Throwable).

### 16. [security] No ownership/authorization check on write (POST/DELETE) — customer IDOR over any record
**`public/api/store.php:48-114`** (php-core)

- **問題:** GET (lines 30-44) and sync.php scope orders/users to the authenticated owner for non-privileged users. The write paths do NOT: POST (lines 48-97) upserts any id into any store, and DELETE (lines 106-114) soft-deletes any id, with no check that current_user()->uid owns the record or that the role is privileged. The shared api_token is embedded in the client bundle/APK (config.sample.php lines 29-34), so any customer — or anyone who extracts the token — can write/delete arbitrary records.
- **影響:** A logged-in customer can overwrite or delete another customer's order, tamper with prices/totals/status in any order, edit other users' records (including their own role/password fields), or wipe arbitrary records one id at a time. Confidentiality is enforced on read but integrity is not enforced on write.
- **修正案:** On POST/DELETE for sensitive stores (orders, users, etc.), call current_user(); reject non-privileged roles unless the target record's userId/id matches $cu['uid'], and forbid customers from setting privileged fields (role/password/status). Require a valid user token for writes once clients are updated.

### 17. [async] Camera stream leaks when scanner closes/unmounts during async startup
**`src/components/staff/ProductQrScanner.tsx:100-111`** (staff-components)

- **問題:** The open effect calls the async startCamera() and returns stopCamera as cleanup. startCamera awaits requestAnimationFrame, dynamic import of @zxing/browser, and decodeFromConstraints (which actually opens the camera) before assigning controlsRef.current = controls and streamRef.current. If the Sheet is closed (open -> false) or the component unmounts before those awaits resolve, the cleanup stopCamera() runs first while controlsRef.current and streamRef.current are still null, so it stops nothing. The pending decodeFromConstraints then resolves and assigns the live controls/stream with no further cleanup, leaving the camera and MediaStream tracks running. This is deterministically triggered by React StrictMode's mount/unmount/remount (staff-main.tsx renders <StrictMode>), and by any quick open-then-close, on the staff Capacitor APK.
- **影響:** Camera stays active (indicator light on) and the MediaStream is leaked after the scanner sheet is closed or the screen is left; repeated open/close accumulates orphaned camera sessions and can prevent the camera from being reacquired until the app is restarted.
- **修正案:** Guard the async startup with a cancellation flag captured in the effect (e.g. let cancelled=false; in cleanup set cancelled=true). After each await and especially after decodeFromConstraints resolves, if cancelled (or !open / video unmounted) immediately call controls.stop() and stop the stream tracks instead of storing them; only assign controlsRef/streamRef when not cancelled.

## 🟠 MEDIUM

### 18. [logic] Stored status "正常" masks an overdue next-inspection date forever
**`src/pages/Admin/AdminMaintenance.tsx:85`** (admin-calendar-ops)

- **問題:** The display status short-circuits on the persisted field: `r.status === "正常" ? "正常" : days < 0 ? "超過" ...`. Once a record's stored status is "正常", the badge always renders "正常" regardless of how overdue the recomputed `days` is. The recomputed `days` is only used for the numeric column and the KPI/alert filters (which key off `r.days`, not status). So a machine whose next-inspection date has passed shows a green "正常" badge in the table even though `days` is negative, and the row is simultaneously counted in the '超過' KPI (filters by days<0) AND in the '正常運用' KPI (filters by status==="正常", line 285). The two KPIs double-count the same record and contradict each other.
- **影響:** Overdue equipment is shown as healthy (green '正常') in the maintenance table, and the '超過' and '正常運用' KPI counts both include the same row, so admins get contradictory totals and may skip a genuinely overdue inspection.
- **修正案:** Derive status purely from the recomputed days (and only treat a fresh inspection as 正常 when days >= 0), e.g. `const status = days < 0 ? "超過" : days <= 7 ? "期限間近" : (r.status === "要修理" ? "要修理" : "正常");`, so an overdue date always overrides a stale stored "正常".

### 19. [date-time] Rental-history date filter compares non-zero-padded order date against zero-padded date input (filter silently wrong)
**`src/components/AdminCustomerManagement.tsx:672-680`** (admin-customer-mgmt)

- **問題:** The 注文日 start/end filter does a lexicographic string comparison between the order's display date and the <input type="date"> value. The order date comes from OrderContext as `new Date().toLocaleDateString("ja-JP")` which produces NON zero-padded `YYYY/M/D` (e.g. `2026/6/9`). The code converts it via `.split(" • ")[0].replace(/\//g, "-")` to `"2026-6-9"`, then compares with `<input type="date">` values which are ALWAYS zero-padded ISO `"2026-06-09"`. Lexicographically `"2026-6-9" > "2026-06-09"` because the 6th character `'6'` > `'0'`. So the comparisons `datePart < rentalStartDateFilter` / `datePart > rentalEndDateFilter` give wrong results for any month or day < 10.
- **影響:** Admins filtering a customer's rental history by order date get incorrect results: orders dated in single-digit months/days are wrongly included or excluded (e.g. an order on 2026/6/9 is treated as later than 2026-06-30). CSV exports of the filtered set and the footer total (line 1353) inherit the wrong row set, so reported amounts can be wrong.
- **修正案:** Normalize the order date to zero-padded ISO before comparing, e.g. parse with parseDateLocal/split into Y-M-D and pad month/day to 2 digits, or compare Date objects instead of strings. Example: const [y,m,d]=datePart.split('-'); const iso=`${y}-${m.padStart(2,'0')}-${d.padStart(2,'0')}`; then compare iso.

### 20. [security] Generated account passwords use non-cryptographic Math.random()
**`src/components/AdminCustomerManagement.tsx:201`** (admin-customer-mgmt)

- **問題:** All auto-generated customer/sub-user passwords (and password resets) are produced with `Math.random().toString(36).slice(-8)`. Math.random() is not a CSPRNG; its output is predictable from observed values and seedable, so generated login passwords are guessable in principle. Same pattern at lines 512 (handleAddSubUser), 564 (bulk add), 641 (handleResetPassword), and AdminUserManagement.tsx line 96.
- **影響:** Customer-portal login passwords created by admins (initial credentials, bulk-imported staff, and password resets) have low/predictable entropy, weakening account security for all customer and customer_staff accounts. Combined with the known plaintext-password storage, this makes credential compromise easier.
- **修正案:** Generate passwords with crypto.getRandomValues (e.g. build from crypto.getRandomValues(new Uint32Array(...)) mapped to an alphabet) instead of Math.random(), and prefer server-side generation/hashing.

### 23. [data-integrity] Non-atomic read-modify-write + stale stock check on 出庫 (oversell / stock drift)
**`src/pages/Admin/AdminStockOut.tsx:90-112`** (admin-vehicles)

- **問題:** handleSaveStockOut validates `onHand < qty` and then writes `Math.max(0, onHand - qty)` using `onHand = Number(match.stock || 0)` from the UI snapshot `match`. Both the availability check and the new value are based on the same possibly-stale snapshot, and patch writes an absolute value (not a decrement).
